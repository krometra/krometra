## Context

Проект на стадии Phase 1 Foundation. Реализованы auth (OAuth2/PKCE), CRUD проектов с изоляцией, каркас Three.js-viewport. Но `Project` хранит только метаданные, `EditorView` не загружает проект, viewport показывает лишь сетку. Документ-модель (ядро CAD-данных, `gdd.md` §6.4), авто-сейв и загрузка меша отсутствуют.

Ограничения и константы:
- Геометрическое ядро (OpenCASCADE/pythonOCC) — отдельная крупная работа с высоким риском (`gdd.md` §9.1), вне этого среза. Значит, сервер пока не может посчитать реальную геометрию.
- Архитектурный принцип (AGENTS.md, `gdd.md` §5.2): геометрию считает сервер, клиент получает тесселированный меш + topology skeleton, не считает B-rep сам.
- Persistence split (`gdd.md` §6.8): метаданные документа — в PostgreSQL, бинарные геометрические данные — в MinIO/S3.
- Безопасность: изоляция по `owner_id` на уровне запроса; токены не трогаем.

## Goals / Non-Goals

**Goals:**
- Замкнуть вертикальный срез «пустой проект → сохраняемый документ → меш в viewport» через все слои.
- Зафиксировать стабильный контракт транспорта меша (`gdd.md` §5.2), который позже реализует OCCT без изменения эндпоинта/формата.
- Сделать настоящими persistence-путь (Postgres JSONB), хранилище меша (MinIO) и render-путь (Three.js), чтобы ядро встало внутрь готового конвейера.
- Авто-сейв с optimistic locking, безопасный к конкурентным вкладкам.

**Non-Goals:**
- Реальная геометрия/OCCT, тесселяция настоящих тел.
- Скетчер, реальные фичи и операции timeline (timeline хранится как непрозрачный массив).
- Интерактивная селекция граней/рёбер (`brepTopo` передаётся и кэшируется, но клик-селекция — позже).
- Экспорт STEP/STL, `project_members`/sharing, триггер авто-сейва «после геом-операции».
- Версионирование документов (история версий) — есть только счётчик `version` для locking.

## Decisions

### 1. Документ как тонкий JSONB-конверт, отдельная таблица 1:1

`documents`: `id`, `project_id` (FK CASCADE, unique), `components` JSONB, `timeline` JSONB, `metadata` JSONB, `version` int, timestamps. Сервер не валидирует внутреннюю форму `components`/`timeline`.

- **Почему отдельная таблица, а не колонка в `projects`:** документ концептуально отделён (CAD-данные vs карточка проекта), потенциально крупный JSONB, и его удобно грузить/сохранять независимо от списка проектов. 1:1 с unique-констрейнтом по `project_id`.
- **Почему тонкий конверт:** фиксировать серверную схему Component/Body/Sketch/Feature под фичи, которых ещё нет, — преждевременно. Типизация живёт на клиенте (`types/api.ts`) и нарастает по мере фич. Сервер — прозрачное хранилище JSON.
- **Альтернативы:** (а) полный типизированный граф на сервере — отвергнут как преждевременный и хрупкий; (б) хранить документ целиком в MinIO как JSON-файл — отвергнут: теряем транзакционность с метаданными и удобство запросов, Postgres JSONB достаточно.

### 2. Optimistic locking по целочисленному `version`

`PUT` принимает `version`; сервис сравнивает с текущим в БД в рамках транзакции, при равенстве пишет и инкрементирует, иначе — `409`.

- **Почему:** защищает от затирания при нескольких вкладках/клиентах (`gdd.md` §6.8, риск auto-save конфликтов) простым и понятным механизмом.
- **Альтернативы:** ETag/If-Match — эквивалентно, но `version` уже фигурирует в модели документа GDD и проще ложится на тонкий конверт; CRDT/OT — это v2-коллаборация, избыточно.

### 3. Контракт меша зафиксирован сейчас, генерация — за интерфейсом `tessellate()`

Эндпоинт `GET /api/projects/{id}/geometry/{body_id}/mesh` возвращает `{ vertices, indices, brepTopo: { faces, edges }, bbox }`. `geometry_service.get_mesh()` обращается к `GeometryEngine.tessellate()`, реализация которого пока возвращает хардкод-куб.

- **Почему так:** задача Foundation — проложить трубу, а не посчитать геометрию. Заглушка прячется ровно за швом, который займёт OCCT (thread C). Контракт меша — публичный и стабильный с этого момента.
- **Альтернатива (отвергнута):** клиент строит примитивы сам (`BoxGeometry`) — нарушает «клиент не считает геометрию», создаёт привычку, которую больно отучать.

### 4. MinIO задействуется сейчас — как кэш меш-блобов

`core/storage.py` — async-клиент MinIO (init bucket при старте). Меш кэшируется по `{projectId}/geometry/{bodyId}.mesh`: при запросе сначала смотрим хранилище, при промахе генерируем через `tessellate()` и кладём блоб.

- **Почему сейчас, а не «отложить»:** делает настоящим именно тот путь хранения геометрии, который по GDD основной для MinIO. Thread C заменит генератор за швом, а путь хранения/чтения/кэша уже отлажен. (Это сознательный выбор в пользу «MinIO now» против варианта отложить до появления реальных `.brep`.)
- **Формат блоба:** сериализованный меш-контракт (JSON или компактный бинарный). Для среза достаточно JSON; бинарный формат (protobuf/glTF) — оптимизация на потом, контракт ответа эндпоинта от этого не зависит.
- **SDK:** предпочесть S3-совместимый async-доступ (`aioboto3`) либо официальный `minio` SDK в thread-pool; выбор фиксируется при реализации, не влияет на контракт.

### 5. Frontend: `useDocument` (shared) + `useAutoSave` (обычный composable)

`useDocument` (createSharedComposable) держит один открытый документ: `document`, `version`, `isDirty`, `conflict`, `load(projectId)`, `save()`. `useAutoSave` — обычный composable с таймером 30с и `watch(isDirty)`, дергает `save()`. `EditorView` оркеструет: грузит документ, запрашивает меш, отдаёт в `ViewportContainer.addMesh()`.

- **Почему два разных уровня:** глобальное состояние документа — синглтон (его видят viewport, browser tree, properties); механика авто-сейва — поведение, привязанное к жизненному циклу редактора, ему не нужен синглтон. Соответствует конвенции (shared только для глобального состояния, не Pinia).

## Risks / Trade-offs

- **Заглушка-куб маскирует реальные проблемы тесселяции/производительности** → контракт намеренно совпадает с будущим выходом OCCT (плоские `vertices`/`indices`/`bbox`), так что объём данных и путь рендеринга реалистичны по форме; нагрузочные характеристики проверяем в thread C.
- **Кэш меша инвалидируется при будущих геом-операциях, а инвалидации ещё нет** → в этом срезе тело статично (куб), инвалидация не требуется; механизм инвалидации кэша — задача thread C (часть feature-regeneration), фиксируем как явный долг.
- **Optimistic locking гонка на самом сравнении версий** → сравнение и запись делать в одной транзакции (`SELECT ... ; if match UPDATE`), при необходимости — атомарный `UPDATE ... WHERE version = :v` с проверкой числа затронутых строк, чтобы исключить TOCTOU.
- **MinIO SDK может быть блокирующим** → не вызывать его напрямую в event loop; использовать async-клиент либо `run_in_executor`. Иначе нарушается принцип «всё async».
- **Рост `documents.components` JSONB при крупных моделях** → приемлемо для MVP; при необходимости документ можно будет вынести в MinIO позже без смены публичного API (load/save остаются те же).
- **Утечки GPU-памяти при пересоздании меша** → `addMesh` обязан `dispose` старых геометрий/материалов; покрыто требованием спеки и проверяется при реализации.

## Migration Plan

1. Alembic-миграция: таблица `documents` (+ unique по `project_id`, FK CASCADE). Применяется через `make migrate`.
2. Бэкфилл: для существующих проектов создать пустые документы (в миграции или ленивым созданием при первом `GET document`, если документа нет). На текущем этапе проектов с данными нет — достаточно создания при `create_project`; ленивое создание добавить как защиту для уже существующих строк.
3. Конфиг: добавить MinIO env (endpoint, ключи, bucket) в `config.py` и `.env.example`; контейнер MinIO уже в `docker-compose.yml`.
4. Rollback: миграция down удаляет таблицу `documents`; MinIO-объекты остаются (безвредны), bucket можно очистить вручную. Фронтовые изменения деградируют до прежнего поведения, если эндпоинты отсутствуют (EditorView должен мягко обрабатывать ошибку загрузки).

## Open Questions

- Формат сериализации меш-блоба в MinIO на старте — JSON или сразу компактный бинарный? (Предложение: JSON сейчас, бинарь — отдельная оптимизация.)
- Выбор SDK для MinIO: `aioboto3` (S3-совместимый, async) против официального `minio` (sync, через executor). Решается при реализации; на контракт не влияет.
- Нужно ли уже в этом срезе отдавать `body_id` из документа (какие тела рендерить), или для заглушки достаточно одного фиксированного `body_id`? (Предложение: один фиксированный куб, перечисление тел из документа — когда появятся реальные тела.)
